# CLAUDE.md — как работать в этом репозитории

Инструкции для Claude Code в этом репозитории. Не про то, что сделано (это
в [HANDOFF.md](HANDOFF.md) и [README.md](README.md) — оба обновлены
2026-09-25 и на тот момент отражали реальное состояние, но оба
обновляются вручную, не автоматически при каждом коммите — если прошло
много времени с этой даты, сверяйся с `git log`, а не считай написанное
здесь вечной истиной), а про то, **как** здесь работать, чтобы не
переоткрывать одни и те же грабли каждую сессию.

## Что это за проект

GridForge — сетевой мониторинг/управление, написан **с нуля**. Не форк
Zabbix (был источником идей, не кода/схемы БД/протокола) и не копия
NetOpsHub (тот же функционал переносится, но переписывается заново —
другие имена сущностей, другая архитектура). Есть тест-сторож
(`tests/test_naming_purity.py`), который проверяет, что в именах классов/
таблиц/полей/путей API не всплывает чужая терминология (`Item`/`Trigger`/
`Host` от Zabbix, `Device`/`Alert` от NetOpsHub) — если он падает, это не
баг теста, это сигнал переименовать.

Стек: Python 3.12/FastAPI/SQLAlchemy, SQLite по умолчанию (MySQL/MariaDB
опционально через `GRIDFORGE_DATABASE_URL`), asyncio. Фронтенд — vanilla
HTML/CSS/JS без шага сборки (`static/*.html` + одноимённый `.js`,
`common.js` — общая шапка/навигация/API-хелперы на все страницы).

Своя терминология (см. докстринг `app/models.py`), не калька с Zabbix:
`Node` (узел), `Probe` (проверка, не "item"), `Sample` (результат, не
"history"), `Watch` (условие, не "trigger"), `Incident` (не "event"/
"problem"), `Signal` (уведомление, не "action").

## Рабочая копия и куда пушить

- Реальная рабочая копия — **WSL Kali**, путь `/tmp/gridforge-app` (из
  Windows: `\\wsl$\kali-linux\tmp\gridforge-app\`). Редактировать файлы
  можно и через Windows-путь, но все `git`/`docker`/`pytest` команды —
  через `wsl -d kali-linux -- bash -c "..."`.
- GitHub: `Madiyar89/gridforge`, **приватный**, ветка `master`. Пушить
  можно свободно — не публичный репозиторий.
- Два развёрнутых инстанса, оба нужно обновлять при каждом деплое:
  - **Локальный** — `/mnt/e/NetOpsHub-scaffold/gridforge-local` (тот же
    WSL), свой `docker-compose.yml`, `git pull` + `docker compose build
    gridforge && docker compose up -d gridforge`.
  - **Боевой** — `192.0.2.10`, пользователь `sysadm`, ключ
    `~/.ssh/netops_244`, путь `~/gridforge-app`. Файлы копируются
    `scp` (не git pull — там нет .git), затем то же
    `docker compose build/up`. Команды на нём всегда через
    `wsl -d kali-linux -- bash -c "ssh -i ~/.ssh/netops_244 sysadm@192.0.2.10 '...'"`.
  - После деплоя проверять `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8100/login.html`
    на каждом (200 = живой) и смотреть `docker logs gridforge --tail N`
    на ошибки миграции/старта.

## Git-коммиты: не используй `-m` с кириллицей напрямую

Инлайновый `git commit -m '...'` с кириллицей + длинным тире/типографскими
кавычками ломает внешнее квотирование `wsl -d kali-linux -- bash -c "..."`
(`unexpected EOF`). Рабочий способ: написать сообщение коммита в
scratchpad-файл (`Write` tool), скопировать в WSL как `/tmp/commit_msg.txt`,
закоммитить `git commit -F /tmp/commit_msg.txt`. Так же для сообщений PR.

Стадь только конкретные файлы (`git add <file> <file>...`), никогда
`git add -A`/`-u` целиком — в рабочей копии годами висят посторонние
незакоммиченные изменения (см. ниже про `vendor/impacket`), которые
случайно утянутся широким add.

## Известная посторонняя грязь в рабочей копии

`git status` в этой рабочей копии годами показывает ~18 удалённых файлов
под `vendor/impacket/*` — это не следствие текущей задачи, предыдущие
сессии это проверяли: файлы физически отсутствуют на диске, но GitHub
(и `git show HEAD:vendor/impacket/...`) их содержит целиком, Docker-сборка
проходит без них (значит, приложение эти конкретные подмодули не
импортирует). Не трогать, не коммитить это удаление, не пытаться чинить
"заодно" — не относится к текущей задаче.

## Тесты: полный набор pytest виснет намертво в этом окружении

`pytest` без фильтра (даже с `--ignore` на медленные файлы) зависает без
вывода на неопределённое время в этой среде — не просто медленно, а
зависает. `pytest-timeout` не установлен (флаг `--timeout` падает как
неизвестный, не помогает). **Рабочий способ**: собрать одноразовый образ
из текущей рабочей копии и прогнать только релевantные тесту файлы:

```bash
cd /tmp/gridforge-app
docker build -t gridforge-test -q .
docker run --rm \
  -v /tmp/gridforge-app/tests:/app/tests \
  -v /tmp/gridforge-app/app:/app/app \
  gridforge-test python -m pytest tests/test_X.py tests/test_Y.py -q
docker rmi gridforge-test   # убрать за собой
```

Монтирование `tests/`/`app/` поверх образа даёт свежий код без пересборки
слоя каждый раз. Выбирай файлы тестов по теме правки плюс пару соседних
для регрессии (auth/login почти всегда стоит зацепить — дёшево и ловит
поломки маршрутизации). Полный прогон не нужен для мелких правок — этот
подход уже использовался десятки раз в разработке, доверять ему можно.

На этой (не-WSL) машине прогон через `venv/bin/python -m pytest` напрямую
работает нормально (не виснет) — Docker-обходной путь выше специфичен
для WSL-окружения, здесь можно проще.

**Порт-конфликт с уже запущенным `gridforge.service`** (реальный
инцидент 2026-09-25): `tests/conftest.py` переопределяет
`GRIDFORGE_SYSLOG_PORT`, но не переопределял `GRIDFORGE_NETFLOW_PORT` —
после появления `app/netflow_server.py` (порт 2055 по умолчанию) тесты
на этой машине начали падать `OSError: [Errno 98] Address already in
use`, потому что боевой `gridforge.service` уже слушает 2055.
Исправлено (`GRIDFORGE_NETFLOW_PORT=15998` в conftest.py) — но правило
на будущее: **любой новый UDP/TCP-порт, который стартует в `lifespan()`,
обязан быть переопределим через переменную окружения и попадать в
`conftest.py`**, иначе тесты рано или поздно столкнутся с живым
сервисом на этой же машине.

## Миграции схемы — ручные, не Alembic

`Base.metadata.create_all()` создаёт только **отсутствующие таблицы**.
Новая **колонка в уже существующей таблице** — руками в
`app/db.py:_migrate_missing_columns()` (`ALTER TABLE ... ADD COLUMN ...`,
идемпотентно, диалект-независимо через `sqlalchemy.inspect`). Забыть это
после первого деплоя таблицы — типичная причина "у меня локально
работает, а на проде колонки нет".

## Устоявшиеся архитектурные идиомы (повторно используй, не изобретай заново)

- **Периодические проверки по расписанию** (день недели + время): смотри
  `VulnScanSchedule`/`run_due_vuln_schedules` (`app/vuln_scan_engine.py`)
  и `CableDiscoverySchedule`/`run_due_cable_discovery_schedules`
  (`app/cable_discovery_engine.py`) — оба проверяются раз в 60с из
  `Scheduler.run_forever()` (`app/scheduler.py`) через отдельный
  `asyncio.create_task()`, не `await` в цикле (иначе встанет опрос
  Probe на всё время долгого прогона). Guard от повторного срабатывания
  в тот же день — строковое поле `last_triggered_on` ("YYYY-MM-DD"),
  выставляется ДО прогона, не после.
- **Восстановление фоновых задач после рестарта**:
  `_recover_interrupted_background_jobs()` в `main.py` (вызывается в
  `lifespan` при каждом старте) помечает всё ещё `status="running"` НА
  МОМЕНТ СТАРТА процесса как прерванное — все реальные фоновые задачи
  создаются уже после этой точки, так что "running" на старте не может
  быть результатом живой задачи. Любой новый `asyncio.create_task()` с
  промежуточным статусом в БД должен встраиваться в этот список.
- **Правка HTML на всех страницах без редактирования каждого файла**:
  когда нужно что-то добавить/убрать на всех 27 `static/*.html` разом
  (favicon был правкой per-file — там нужен `<link>` до загрузки
  common.js), а когда можно — JS-инъекция из `common.js` в `initTopbar()`
  (так сделаны `.brand-badge`, `#sidebar-pin`, `#user-avatar`, удаление
  теглайна) — один файл вместо 27. `login.html` **не подключает**
  `common.js` (отдельная форма входа до авторизации) — для правок,
  которые должны быть и там, нужен per-file подход.
- **Опрос сетевых устройств**: единая точка — `app/device_client.py`
  (`run_device_command`), транспорт (SSH/Telnet) выбирается по
  `Node.vendor`, не вызывающим кодом. Пароли/ключи — через
  `resolve_credential(db, node)` (`app/credentials_engine.py`), не
  спрашивать пользователя заново, если для узла/группы уже настроена
  центральная учётка.
- **Имена интерфейсов бывают в двух форматах** — полное
  ("GigabitEthernet1/0/48", так отдаёт `show cdp neighbors detail`) и
  сокращённое ("Gi1/0/48", так хранит `PortSnapshot` из `show interfaces
  status`). Сравнивать напрямую строками — гарантированный баг (реальный
  случай 2026-09-24: автоопрос кабелей находил 0 совпадений на живом
  парке из-за этого). Всегда через `normalize_iface()`
  (`app/ports_engine.py`).
- **Массовый опрос группы узлов параллельно**: `asyncio.Semaphore` на
  8 одновременных SSH-сессий (см. `sweep_engine.py`, `hub_detection_engine.py`,
  `cable_discovery_engine.py`) — не увеличивать без причины, часть парка
  (старые 2950/2960) плохо переносит параллельные подключения.
- **RBAC по группе узлов**: любой эндпоинт, читающий/пишущий данные
  конкретной группы, обязан звать `key_sees_group(key, group_id)` —
  ограниченный по группе API-ключ должен получать 403 на чужую группу,
  не 404 (тест-сторож это проверяет по всем маршрутам из OpenAPI-схемы,
  см. HANDOFF.md §5).
- **Уведомление в обход Incident**: `Incident` жёстко привязан к `Watch`
  на `Probe` на уже существующем `Node` (см. терминологию наверху) —
  событие, у которого нет узла (например "найдено новое устройство",
  ещё не заведённое как Node), заводить как Incident было бы смысловой
  натяжкой. Для таких случаев — свой лёгкий путь мимо `signal.dispatch()`,
  см. `signal.notify_new_devices()`: переиспользует только расшифровку
  `Channel.config` и рассылку по `ChannelKind`, без формирования Incident.
  Уходит на все включённые каналы БЕЗ `node_id`/`watch_id` (сужение по
  конкретному узлу для события без узла бессмысленно).

## ПРОДОЛЖИТЬ ЗДЕСЬ — состояние на 2026-09-25

Владелец подтвердил порядок: Nuclei → Feroxbuster → отдельное
обсуждение NetExec. Все три доведены до конца и проверены вживую —
третий не в виде самого NetExec (см. ниже, почему), а узким срезом его
функции напрямую через impacket.

### Nuclei — готово, проверено вживую 2026-09-25

Прошлая сессия оставила код написанным, но непроверенным (шаблоны не
скачивались из-за таймаута). При продолжении на другой машине живой
прогон сразу же вскрыл два реальных бага, которых не видно по
документации:

1. **`-l "-"` не читает цели из stdin** — эта версия nuclei понимает
   под `-l` только путь к файлу ("could not open targets file: open -:
   no such file or directory"). Исправлено: флаг убран целиком, nuclei
   сам распознаёт пайпнутый stdin как список целей, если ни `-l`, ни
   `-u` не заданы (подтверждено живым запуском).
2. **nuclei возвращает `returncode=0` даже на фатальную ошибку** —
   "no templates provided for scan" тоже exit 0. Раньше это означало бы
   тихое "скан выполнен, находок 0" вместо честного failed. Исправлено:
   `run_nuclei_scan` дополнительно ищет `"FTL"` в stderr (не `"FTL]"` —
   между уровнем лога и закрывающей скобкой у nuclei вставлен ANSI-код
   сброса цвета, проверено побайтово через `repr()` вывода, не на глаз).

**Шаблоны** — оказалось, дело не в разовой перегрузке сети (as прошлая
сессия предполагала про `apt-mirror`), а в системном ограничении
корпоративного прокси: он обрывает ЛЮБУЮ передачу крупнее ~5МБ
(перепроверено на двух разных машинах этой инфраструктуры одинаковым
результатом — `stream error`/`connection reset by peer` что у
`nuclei -update-templates`, что у голого `curl` на codeload.github.com/
GitHub release assets; `codeload` к тому же не поддерживает Range —
докачать оборванное тоже нельзя). Рабочий обход: `git clone --depth 1`
того же контента (smart-HTTP, другая передача данных) прошёл без единой
ошибки на всех ~14000 файлах. `Dockerfile` теперь клонирует шаблоны в
`/root/nuclei-templates` при сборке образа (не на первом старте
контейнера — тот же принцип, что у offline-GeoLite2), а бинарник nuclei
ставится тем же способом, что уже применяла эта сессия для похожих
случаев — релизный .zip с GitHub (укладывается в лимит прокси, ~6-7МБ).

**Живая проверка (дважды)**: точечный прогон (`-tags tech` против
`scanme.nmap.org`, легальная тестовая цель) поймал и корректно разобрал
реальную находку (`apache-detect`, severity `info`) — `parse_nuclei_jsonl()`
подтверждён на настоящем JSON, не только на документированной схеме.
Полный прогон (все ~14000 шаблонов) через `run_nuclei_scan()` целиком,
от `POST`-эквивалента до записи в БД — `VulnScan.status=done`,
`VulnScanHost` записан, без ошибок. Докстринг в начале
`vuln_scan_engine.py` обновлён по факту проверки.

### Feroxbuster — готово, проверено вживую 2026-09-25

Реализовано по уже согласованному с владельцем плану: `run_web_discovery_scan()`
рядом с `run_nuclei_scan()`, профиль `"web_discovery"`. Для каждого
узла сначала `_probe_http_urls()` — быстрый TCP-коннект на 80/443/8080/
8443 (не полноценный HTTP-запрос — дешевле, не гонять feroxbuster
вслепую по адресам без веб-сервера), затем по каждому найденному URL
отдельный прогон `feroxbuster -w <свой словарь> --json --silent -d 1`
(без рекурсии в подпапки — верхний уровень, тот же принцип "для
человека", что и severity="info" у всех находок). Свой словарь —
`app/wordlists/web_discovery.txt` (~250 строк: конфиги/бэкапы/.git/.env/
админки/API-эндпоинты), не SecLists — офлайн, без внешней закачки при
сборке или в рантайме.

`Dockerfile`: тот же путь, что у бинарника nuclei (релизный .zip с
GitHub, версия зафиксирована) — feroxbuster тоже kali-only apt-пакет,
в Debian slim его нет. `--json` у feroxbuster обязательно требует ещё
и `--output`/`--debug-log`/`--silent` (иначе ошибка валидации аргументов
CLI — узнано только живым запуском, не из `--help`).

**Живая проверка**: `run_web_discovery_scan()` целиком, от вызова до
записи в БД, против собственного тестового HTTP-сервера с реальными
`.env`/`.git`/`admin.php`/`robots.txt` — все найдены и верно разобраны
(`.git` — 301 редирект на `/.git/`, тоже корректно учтён). По пути
обнаружился посторонний Apache на порту 80 хоста тестовой машины —
не баг GridForge, подтвердило только, что многопортовый проб
(`FEROX_CANDIDATE_PORTS`) реально пробует все 4 порта, а не только
первый попавшийся.

### NetExec → CredentialCheckRun — готово, проверено вживую 2026-09-25

Сознательно НЕ CrackMapExec (тот мёртв с 2023, все идут на форк
NetExec, `Pennyw0rth/NetExec`, тот же BSD-2-Clause). В отличие от
Nuclei/Feroxbuster (пассивное обнаружение) — это активная проверка
реальных учётных данных на реальных машинах, заметно более
чувствительная вещь. Обсудили с владельцем объём: только проверка
SMB-логина (успех/отказ), без выполнения команд и без модулей дампа
секретов — самый узкий срез из всего, что умеет NetExec.

**Почему НЕ сам NetExec**: живая попытка `pip install git+https://github.com/Pennyw0rth/NetExec`
уперлась в тот же прокси-обрыв больших закачек, что уже решался
вендорингом impacket — но здесь дерево зависимостей на порядок шире:
`impacket` (снова из git), `bloodhound_ce`, `pypykatz`, `dploot`,
`certipy-ad`, `certihound`, `dsinternals`, `aardwolf`, `aiosmb`,
`msldap` и ещё десятки — вендорить весь этот список ради функции
"проверить один SMB-логин" несоразмерно, тем более что подавляющее
большинство этих пакетов — инструментарий для AD-атак (BloodHound,
Mimikatz-подобный pypykatz, дамп DPAPI-секретов dploot), который мы и
так сознательно не берём по объёму. Решение: не тянуть NetExec целиком
ради узкого куска функциональности, а реализовать этот кусок напрямую
через уже вендоренный `impacket.smbconnection` — тот же примитив, что
уже работает в `domain_scan_engine.py` (`_query_smb_sync`).

**Реализовано**: `CredentialCheckRun`/`CredentialCheckTarget` в
models.py, `app/credential_check_engine.py`
(`run_credential_check`/`_check_smb_login_sync`), эндпоинты
`POST /api/groups/{id}/credential-checks` (требует
`consent_confirmed: true`, иначе 400) + `GET .../credential-checks` +
`GET /api/credential-checks/{id}/targets`, страница
`credential-check.html` ("Проверка доступа" в Разведке) — группа,
логин/пароль/домен вводятся заново при каждом запуске (пароль нигде
не хранится, даже в зашифрованном виде), обязательный чекбокс согласия
блокирует кнопку запуска, журнал прогона хранит `triggered_by`
(`Principal.label` запросившего) — кто/когда/какой логин пробовали
(пароль — никогда).

**Живая проверка**: реальный Samba-сервер (`dperson/samba` в Docker),
три сценария — верный пароль (успех), неверный пароль (`ok=False`,
честный `STATUS_LOGON_FAILURE` от SMB), недоступный порт (`ok=False`,
`Connection refused`). Первая попытка теста с "заведомо недоступным"
IP (`10.255.255.254`) сама неожиданно законнектилась — не баг кода, а
особенность Docker-сети в этом окружении (адрес оказался
маршрутизируемым); заменено на реально остановленный сервер для
честной проверки отказа.

## Тон разработки

Каждая фича этой сессии проверялась не только компиляцией/юнит-тестами,
а живым вызовом на реальном железе/реальных данных, когда это было
возможно (реальный CDP-вывод с прод-свитча поймал баг, который синтетика
в тестах пропустила). Если правишь код, разбирающий вывод сетевого
устройства — искать реальный пример вывода стоит раньше, чем писать
регэксп по памяти.
