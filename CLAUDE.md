# CLAUDE.md — как работать в этом репозитории

Инструкции для Claude Code в этом репозитории. Не про то, что сделано (это
в [HANDOFF.md](HANDOFF.md) и [README.md](README.md), но оба обновлялись
вручную и отстают от реального состояния — сверяйся с `git log`, если
нужна точная картина), а про то, **как** здесь работать, чтобы не
переоткрывать одни и те же грабли каждую сессию.

## Что это за проект

GridForge — сетевой мониторинг/управление, написан **с нуля**. Не форк
Zabbix (был источником идей, не кода/схемы БД/протокола) и не копия
NetOpsHub (тот же функционал переносится, но переписывается заново —
другие имена сущностей, другая архитектура). Есть тест-сторож
(`tests/test_naming_purity.py`), который проверяет, что в именах классов/
таблиц/полей/путей API не всплывает чужая терминология (`Item`/`Trigger`/
`Host` от Zabbix, `Device`/`Alert` от NetOpsHub) — если он падает, это не
баг теста, это сигнал переименовать.

Стек: Python 3.12/FastAPI/SQLAlchemy, SQLite по умолчанию (MySQL/MariaDB
опционально через `GRIDFORGE_DATABASE_URL`), asyncio. Фронтенд — vanilla
HTML/CSS/JS без шага сборки (`static/*.html` + одноимённый `.js`,
`common.js` — общая шапка/навигация/API-хелперы на все страницы).

Своя терминология (см. докстринг `app/models.py`), не калька с Zabbix:
`Node` (узел), `Probe` (проверка, не "item"), `Sample` (результат, не
"history"), `Watch` (условие, не "trigger"), `Incident` (не "event"/
"problem"), `Signal` (уведомление, не "action").

## Рабочая копия и куда пушить

- Реальная рабочая копия — **WSL Kali**, путь `/tmp/gridforge-app` (из
  Windows: `\\wsl$\kali-linux\tmp\gridforge-app\`). Редактировать файлы
  можно и через Windows-путь, но все `git`/`docker`/`pytest` команды —
  через `wsl -d kali-linux -- bash -c "..."`.
- GitHub: `Madiyar89/gridforge`, **приватный**, ветка `master`. Пушить
  можно свободно — не публичный репозиторий.
- Два развёрнутых инстанса, оба нужно обновлять при каждом деплое:
  - **Локальный** — `/mnt/e/NetOpsHub-scaffold/gridforge-local` (тот же
    WSL), свой `docker-compose.yml`, `git pull` + `docker compose build
    gridforge && docker compose up -d gridforge`.
  - **Боевой** — `192.0.2.244`, пользователь `sysadm`, ключ
    `~/.ssh/netops_244`, путь `~/gridforge-app`. Файлы копируются
    `scp` (не git pull — там нет .git), затем то же
    `docker compose build/up`. Команды на нём всегда через
    `wsl -d kali-linux -- bash -c "ssh -i ~/.ssh/netops_244 sysadm@192.0.2.244 '...'"`.
  - После деплоя проверять `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8100/login.html`
    на каждом (200 = живой) и смотреть `docker logs gridforge --tail N`
    на ошибки миграции/старта.

## Git-коммиты: не используй `-m` с кириллицей напрямую

Инлайновый `git commit -m '...'` с кириллицей + длинным тире/типографскими
кавычками ломает внешнее квотирование `wsl -d kali-linux -- bash -c "..."`
(`unexpected EOF`). Рабочий способ: написать сообщение коммита в
scratchpad-файл (`Write` tool), скопировать в WSL как `/tmp/commit_msg.txt`,
закоммитить `git commit -F /tmp/commit_msg.txt`. Так же для сообщений PR.

Стадь только конкретные файлы (`git add <file> <file>...`), никогда
`git add -A`/`-u` целиком — в рабочей копии годами висят посторонние
незакоммиченные изменения (см. ниже про `vendor/impacket`), которые
случайно утянутся широким add.

## Известная посторонняя грязь в рабочей копии

`git status` в этой рабочей копии годами показывает ~18 удалённых файлов
под `vendor/impacket/*` — это не следствие текущей задачи, предыдущие
сессии это проверяли: файлы физически отсутствуют на диске, но GitHub
(и `git show HEAD:vendor/impacket/...`) их содержит целиком, Docker-сборка
проходит без них (значит, приложение эти конкретные подмодули не
импортирует). Не трогать, не коммитить это удаление, не пытаться чинить
"заодно" — не относится к текущей задаче.

## Тесты: полный набор pytest виснет намертво в этом окружении

`pytest` без фильтра (даже с `--ignore` на медленные файлы) зависает без
вывода на неопределённое время в этой среде — не просто медленно, а
зависает. `pytest-timeout` не установлен (флаг `--timeout` падает как
неизвестный, не помогает). **Рабочий способ**: собрать одноразовый образ
из текущей рабочей копии и прогнать только релевantные тесту файлы:

```bash
cd /tmp/gridforge-app
docker build -t gridforge-test -q .
docker run --rm \
  -v /tmp/gridforge-app/tests:/app/tests \
  -v /tmp/gridforge-app/app:/app/app \
  gridforge-test python -m pytest tests/test_X.py tests/test_Y.py -q
docker rmi gridforge-test   # убрать за собой
```

Монтирование `tests/`/`app/` поверх образа даёт свежий код без пересборки
слоя каждый раз. Выбирай файлы тестов по теме правки плюс пару соседних
для регрессии (auth/login почти всегда стоит зацепить — дёшево и ловит
поломки маршрутизации). Полный прогон не нужен для мелких правок — этот
подход уже использовался десятки раз в разработке, доверять ему можно.

## Миграции схемы — ручные, не Alembic

`Base.metadata.create_all()` создаёт только **отсутствующие таблицы**.
Новая **колонка в уже существующей таблице** — руками в
`app/db.py:_migrate_missing_columns()` (`ALTER TABLE ... ADD COLUMN ...`,
идемпотентно, диалект-независимо через `sqlalchemy.inspect`). Забыть это
после первого деплоя таблицы — типичная причина "у меня локально
работает, а на проде колонки нет".

## Устоявшиеся архитектурные идиомы (повторно используй, не изобретай заново)

- **Периодические проверки по расписанию** (день недели + время): смотри
  `VulnScanSchedule`/`run_due_vuln_schedules` (`app/vuln_scan_engine.py`)
  и `CableDiscoverySchedule`/`run_due_cable_discovery_schedules`
  (`app/cable_discovery_engine.py`) — оба проверяются раз в 60с из
  `Scheduler.run_forever()` (`app/scheduler.py`) через отдельный
  `asyncio.create_task()`, не `await` в цикле (иначе встанет опрос
  Probe на всё время долгого прогона). Guard от повторного срабатывания
  в тот же день — строковое поле `last_triggered_on` ("YYYY-MM-DD"),
  выставляется ДО прогона, не после.
- **Восстановление фоновых задач после рестарта**:
  `_recover_interrupted_background_jobs()` в `main.py` (вызывается в
  `lifespan` при каждом старте) помечает всё ещё `status="running"` НА
  МОМЕНТ СТАРТА процесса как прерванное — все реальные фоновые задачи
  создаются уже после этой точки, так что "running" на старте не может
  быть результатом живой задачи. Любой новый `asyncio.create_task()` с
  промежуточным статусом в БД должен встраиваться в этот список.
- **Правка HTML на всех страницах без редактирования каждого файла**:
  когда нужно что-то добавить/убрать на всех 27 `static/*.html` разом
  (favicon был правкой per-file — там нужен `<link>` до загрузки
  common.js), а когда можно — JS-инъекция из `common.js` в `initTopbar()`
  (так сделаны `.brand-badge`, `#sidebar-pin`, `#user-avatar`, удаление
  теглайна) — один файл вместо 27. `login.html` **не подключает**
  `common.js` (отдельная форма входа до авторизации) — для правок,
  которые должны быть и там, нужен per-file подход.
- **Опрос сетевых устройств**: единая точка — `app/device_client.py`
  (`run_device_command`), транспорт (SSH/Telnet) выбирается по
  `Node.vendor`, не вызывающим кодом. Пароли/ключи — через
  `resolve_credential(db, node)` (`app/credentials_engine.py`), не
  спрашивать пользователя заново, если для узла/группы уже настроена
  центральная учётка.
- **Имена интерфейсов бывают в двух форматах** — полное
  ("GigabitEthernet1/0/48", так отдаёт `show cdp neighbors detail`) и
  сокращённое ("Gi1/0/48", так хранит `PortSnapshot` из `show interfaces
  status`). Сравнивать напрямую строками — гарантированный баг (реальный
  случай 2026-09-24: автоопрос кабелей находил 0 совпадений на живом
  парке из-за этого). Всегда через `normalize_iface()`
  (`app/ports_engine.py`).
- **Массовый опрос группы узлов параллельно**: `asyncio.Semaphore` на
  8 одновременных SSH-сессий (см. `sweep_engine.py`, `hub_detection_engine.py`,
  `cable_discovery_engine.py`) — не увеличивать без причины, часть парка
  (старые 2950/2960) плохо переносит параллельные подключения.
- **RBAC по группе узлов**: любой эндпоинт, читающий/пишущий данные
  конкретной группы, обязан звать `key_sees_group(key, group_id)` —
  ограниченный по группе API-ключ должен получать 403 на чужую группу,
  не 404 (тест-сторож это проверяет по всем маршрутам из OpenAPI-схемы,
  см. HANDOFF.md §5).

## Тон разработки

Каждая фича этой сессии проверялась не только компиляцией/юнит-тестами,
а живым вызовом на реальном железе/реальных данных, когда это было
возможно (реальный CDP-вывод с прод-свитча поймал баг, который синтетика
в тестах пропустила). Если правишь код, разбирающий вывод сетевого
устройства — искать реальный пример вывода стоит раньше, чем писать
регэксп по памяти.
