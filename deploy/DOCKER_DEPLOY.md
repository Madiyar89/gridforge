# Docker-развёртывание (2026-09-21)

Помимо systemd-варианта (`deploy/gridforge.service`, для локальной машины) —
Docker-путь для развёртывания на общих/боевых серверах, где нельзя ставить
пакеты в систему напрямую (см. инцидент в дневнике `gridforge-zabbix-fork`
про случайно остановленную MariaDB на `.244` — с тех пор только так).

```bash
docker compose build
docker compose up -d
docker logs gridforge   # тут при первом запуске покажет Admin-пароль и API-ключ — сохранить сразу
```

- Порт **8100** (веб/API) публикуется только на `127.0.0.1` хоста —
  снаружи по сети напрямую недостижим (закрыто, чтобы `X-API-Key` не
  ходил открытым текстом по HTTP через LAN). **5140/UDP** — syslog, без
  изменений.
- Перед 8100 стоит `caddy` (`image: caddy:2-alpine`, `Caddyfile` в корне
  репозитория) — реверс-прокси с терминацией TLS на порту **8443**,
  `tls internal` (встроенный самоподписанный CA Caddy — внутренняя сеть
  без внешнего домена, ACME тут неприменим). Сертификаты хранятся в
  volume'ах `caddy_data`/`caddy_config` и переживают пересоздание
  контейнера (иначе каждый редеплой означал бы новый сертификат и
  повторное предупреждение в браузере).
- Доступ с другой машины (браузер/API) — **`https://<host>:8443`**. При
  первом обращении браузер покажет предупреждение о самоподписанном
  сертификате — это ожидаемо для внутреннего развёртывания без
  публичного CA, нужно принять исключение. `http://<host>:8100` с другой
  машины больше не работает — сделано намеренно. Локальные
  проверки/curl на самом хосте (`http://127.0.0.1:8100/...`, см.
  CLAUDE.md) продолжают работать как раньше.
- БД — SQLite в volume `gridforge_data` (не MariaDB, это дефолт самого
  проекта, см. `app/db.py` — `GRIDFORGE_DATABASE_URL` можно переопределить
  на MySQL, если понадобится).
- `nmap`/`tshark` (для `scan_engine.py`/`capture_engine.py`) — внутри
  образа, с `cap_add: NET_RAW, NET_ADMIN` в compose (не полный root, и
  только для `gridforge` — сервису `caddy` эти capability не нужны).
- Если сеть, где собирается образ, использует TLS-инспекцию (корпоративный
  или гос. root CA подставляется вместо реального сертификата сайта) — `pip`
  при сборке будет падать на TLS-хендшейке. Решение: положить свой corporate
  CA (`.crt`/`.pem`) в `certs/` (см. `certs/README.md`) — `Dockerfile`
  подхватит его через `update-ca-certificates` при сборке. Файл в `certs/`
  не коммитится (`.gitignore`), в самом репозитории конкретного сертификата
  нет — только этот механизм.
- Развёрнуто и проверено на **192.0.2.10** (снаружи — порт 8443 через
  caddy, доп. к уже работающему там NetOps Hub/GridForge-Zabbix-fork/
  phonebook — конфликтов портов нет).
