# GridForge — с чего начать (для того, кто продолжает работу)

Короткая памятка. Полный технический контекст — в `CLAUDE.md`, раздел
**«ПРОДОЛЖИТЬ ЗДЕСЬ»** (ближе к концу файла) — прочитать целиком перед
началом, там объяснения, не только факты.

## 1. Синхронизироваться

```bash
cd gridforge && git pull origin master
```

Последний коммит на момент паузы — `54feafb`.

## 2. Проверить окружение

```bash
source venv/bin/activate  # или создать заново — README.md, раздел «Запуск»
pytest tests/test_naming_purity.py tests/test_api_auth.py -q
```

Должно быть всё зелёным. Если `test_naming_purity` красный — куда-то
залезла терминология Zabbix/NetOpsHub, это сигнал переименовать, не
ослаблять тест.

## 3. Что сейчас в работе — профиль Nuclei в проверке уязвимостей

Код написан (`app/vuln_scan_engine.py`: `run_nuclei_scan`/
`parse_nuclei_jsonl`), но **ни разу не проверен на реальном выводе** —
на предыдущей машине `nuclei -update-templates` не мог скачать базу
шаблонов из-за нехватки полосы (параллельно качалось зеркало Kali).

Первым делом:

```bash
nuclei -update-templates
find ~/.local/nuclei-templates -name "*.yaml" | wc -l   # должно быть тысячи, не 0
```

Если шаблоны скачались — прогнать реальный тест (шаги расписаны в
`CLAUDE.md`), свериться, что находки разбираются правильно, и только
потом убрать предупреждение "живой прогон не подтверждён" из докстринга
`app/vuln_scan_engine.py`.

## 4. Отдельная проблема — Dockerfile

`Dockerfile` собран на `python:3.12-slim` (обычный Debian) —
`nuclei`/`feroxbuster` ставятся через `apt` только на Kali, в Debian
slim их нет. Для Docker-развёртывания нужен другой способ (например,
бинарник с GitHub Releases). Не трогать `Dockerfile` вслепую — сначала
разобраться, что вообще нужно для сборки.

## 5. Порядок дальнейшей работы (уже согласован с владельцем)

**Nuclei → Feroxbuster → NetExec.**

NetExec — последний и самый чувствительный (активная проверка чужих
учётных данных на сети, не пассивное сканирование) — перед кодом ещё
раз обсудить с владельцем область применения, не начинать кодить сразу.

## 6. Общее правило проекта

Каждая фича должна быть проверена **вживую** (реальный вызов, не только
компиляция/юнит-тест), прежде чем считаться готовой. Если проверить
прямо сейчас нельзя — честно писать в коде/коммите, что не проверено
(как уже сделано с Nuclei). Не выдавать непроверенное за готовое.
