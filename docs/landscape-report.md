# Что GridForge может позаимствовать у восьми открытых проектов

Аналитика, сентябрь 2026. Обзор [Sniffnet](https://github.com/GyulyVGC/sniffnet),
[Fort Firewall](https://github.com/tnodir/fort), [Arkime](https://github.com/arkime/arkime),
[LibreNMS](https://github.com/librenms/librenms), [ntopng](https://github.com/ntop/ntopng),
[OpenWISP Controller](https://github.com/openwisp/openwisp-controller),
[LibreDB Studio](https://github.com/libredb/libredb-studio) и
[NetAlertX](https://github.com/netalertx/NetAlertX) — с прицелом на конкретные
улучшения GridForge, а не общий пересказ README.

Составлено на основе публичных README и описаний репозиториев по состоянию
на сентябрь 2026. Обзор не заменяет due diligence по лицензиям (GPL-3.0 у
Fort и Arkime, AGPL/иные условия у остальных стоит перепроверить перед
встраиванием кода, не только идей).

## Итог одним взглядом

GridForge уже закрывает то, что в этих проектах разнесено по разным
инструментам: инвентарь+опрос (как LibreNMS), бэкапы и Port Security
(сильнее, чем у большинства), сканирование уязвимостей с расписанием, журнал
кабельных соединений с CDP-автоопросом. По охвату ближе к LibreNMS + часть
OpenWISP, чем к «маленькому самопальному монитору».

Три направления, где разрыв реальный, а не косметический:

1. **Непрерывное обнаружение новых/неизвестных устройств в сети** (NetAlertX)
2. **Анализ трафика по потокам — NetFlow/sFlow, а не разовые PCAP** (ntopng, Arkime, Sniffnet)
3. **Охват каналов уведомлений** (NetAlertX через Apprise — 80+ сервисов одной библиотекой вместо ручной интеграции каждого)

Полную архитектуру ни одного из них копировать не стоит — см. §5, что
сознательно пропущено.

## Профили проектов

### NetAlertX

Python · self-hosted · Apprise · GraphQL/REST

Непрерывное обнаружение устройств в сети (ARP-сканирование, импорт
DHCP-аренд, интеграция с Pi-hole/Unifi, SNMP-опрос роутеров) с оповещением
о новых/незнакомых устройствах и дрейфе IP. «Sync Node» реплицирует
инвентарь с удалённых площадок в центральный хаб — модель для MSP, у
которых десятки клиентских сетей.

**Ключевое:** 6 независимых методов обнаружения устройств · 80+ каналов
уведомлений через Apprise одной интеграцией · правила автогруппировки по
вендору, автоархивация офлайн-устройств · Prometheus-метрики «из коробки».

**Не хватает у GridForge:** нет фонового «кто новый в сети» — Probe
опрашивает только уже добавленные узлы · каждый канал уведомлений (Signal)
интегрируется вручную, а не через готовую библиотеку · нет модели
мульти-сайта — каждый GridForge живёт сам по себе.

**Для GridForge:** самый прямой источник идей из всей восьмёрки. См.
рекомендации §4.1 и §4.2.

### ntopng

C++ · NetFlow/sFlow/IPFIX · Docker/K8s-native

Веб-панель непрерывного анализа трафика: принимает потоковые данные
(NetFlow/sFlow/IPFIX) или снимает пакеты через eBPF, строит картину «кто с
кем и сколько передал» по хостам и приложениям в реальном времени, а не по
запросу.

**Ключевое:** приём NetFlow/sFlow/IPFIX от существующих коммутаторов/
роутеров без агентов · eBPF — захват без модулей ядра · атрибуция трафика
по приложению/хосту непрерывно, не разовым снимком.

**Не хватает у GridForge:** Capture (tshark) — только разовый запуск на
конкретном узле, не постоянный сборщик потоков · нет истории трафика —
только точечные .pcap-снимки · нет «топ говорящих» дашборда.

**Для GridForge:** самый крупный содержательный разрыв. Большинство
сетевого железа в этом парке (Cisco 9300 и т.п.) уже умеет отдавать
NetFlow — не нужен агент на каждом узле. См. §4.5 (среднее вложение, не
«сделать как ntopng целиком»).

### LibreNMS

PHP/MySQL · SNMP-автообнаружение

Классическая NMS: автообнаружение устройств по SNMP, готовые парсеры для
десятков вендоров, RRD-графики, алертинг, биллинговые счётчики трафика.
Зрелый проект с большим комьюнити-каталогом устройств.

**Ключевое:** огромная база готовых SNMP-профилей устройств
(community-driven) · автообнаружение топологии по LLDP/CDP/SNMP уже
встроено как основной механизм · биллинг/учёт трафика по портам.

**Не хватает у GridForge:** GridForge опирается на SSH-команды (show ...),
не на SNMP-опрос метрик — работает, но каждый новый вендор требует свой
парсер вручную · нет каталога «профилей устройств» — конфигурация каждого
узла по сути ручная.

**Для GridForge:** прямое копирование архитектуры не нужно — SSH-подход
GridForge для Port Security/бэкапов даёт то, что SNMP не даёт (можно
менять конфигурацию, не только читать). Факт, что CDP уже используется
LibreNMS для топологии, подтверждает: решение для журнала кабелей выбрано
в верном направлении.

### Arkime

C + OpenSearch/Elasticsearch · distributed sensors

Полнопакетный захват в промышленном масштабе (гигабиты/с) с индексацией
метаданных сессий в OpenSearch — вывод не графики, а «найди мне все сессии
с этим хостом за последний месяц» с возможностью скачать точный .pcap.
Родом из AOL, замена дорогим коммерческим NDR-решениям.

**Ключевое:** индексированный полнотекстовый поиск по сетевым сессиям в
масштабе всей сети · распределённые сенсоры + центральный viewer ·
cont3xt/wiseService — обогащение находок Threat Intel.

**Не хватает у GridForge:** полностью отсутствует «поиск по прошлому
трафику» — только текущий Capture · нет retention-политики для сырых
пакетов.

**Для GridForge:** архитектуру (кластер OpenSearch + сенсоры) заводить не
стоит — не тот масштаб и не та эксплуатационная модель. См. §5.

### Sniffnet

Rust · iced GUI · MaxMind GeoIP

Настольное приложение «поставил — сразу видно трафик этой машины»:
определение 6000+ протоколов/сервисов/троянов, гео-локация и ASN удалённых
хостов, привязка трафика к конкретным программам, экспорт в .pcap.

**Ключевое:** протокол/сервис/вредонос распознаются автоматически по
сигнатурам · GeoIP + ASN прямо в интерфейсе, без ручного lookup ·
привязка трафика к процессу на хосте.

**Не хватает у GridForge:** в панели «Находки» (Уязвимости) и Capture нет
геолокации/ASN для внешних IP · нет сигнатурного определения сервиса/
трояна по трафику — только nmap-профили.

**Для GridForge:** прямая архитектура не переносится (Sniffnet — desktop-
агент на конечном хосте, GridForge — сетевой монитор), но идея «показывать
GeoIP/ASN рядом с IP» дешева и применима везде, где GridForge уже
показывает адреса — Syslog, Capture, будущий NetFlow-дашборд.

### OpenWISP Controller

Python/Django · OpenWRT-first

Централизованное провижининг-решение для флотов OpenWRT-устройств:
шаблонные конфигурации, push (SSH) и pull (агент на устройстве) доставка,
автоматический выпуск/отзыв X.509-сертификатов, управление VPN mesh.

**Ключевое:** двойная модель доставки конфигурации — push и pull · PKI
полностью автоматизирован (выпуск, деплой, отзыв) · часть экосистемы
(мониторинг, RADIUS, IPAM, топология — отдельные пакеты).

**Не хватает у GridForge:** Templates/Scenarios — это push-only рассылка
команд, нет pull-агента для устройств без постоянной доступности по SSH ·
нет управления сертификатами устройств вообще.

**Для GridForge:** релевантно только если в парке появятся WiFi AP/CPE,
которые нельзя всегда достать по SSH напрямую (за NAT, за мобильной
сетью). Для текущего парка (управляемые Cisco-свитчи) — низкий приоритет.

### LibreDB Studio

SQL IDE · 17+ движков БД

Не сетевой инструмент — браузерная SQL-IDE. Включён в обзор не за
функциональность, а за архитектурный приём: ИИ-агент отвечает на вопросы
по данным и пишет отчёт со ссылками на источники, при этом «только
чтение» обеспечено не фильтром текста запроса, а на уровне транзакции
самой СУБД (READ ONLY-транзакция, откат в конце) — агент физически не
может ничего изменить, даже если промпт его обманет.

**Ключевое:** «спроси вопрос — получи отчёт со ссылками на конкретные
строки» · read-only гарантирован драйвером/транзакцией, не парсингом SQL ·
RBAC + OIDC SSO + журнал аудита действий, доступны без деления на платный/
бесплатный тариф.

**Не хватает у GridForge:** нет ИИ-слоя над уже накопленными данными
(находки уязвимостей, аудит, бэкапы, журнал кабелей) · авторизация —
только LDAP/локальные учётки, нет OIDC SSO.

**Для GridForge:** не про код, про паттерн. У GridForge уже достаточно
структурированных данных, чтобы «спроси про сеть» имело смысл — см. §4.9,
стратегическая, не срочная идея.

### Fort Firewall

C · Windows kernel driver

Персональный firewall для Windows с собственным kernel-драйвером: правила
по приложению/родительскому процессу/сервису, ограничение скорости по
группам приложений, блок-листы по зонам.

Другая предметная область — управление трафиком одного Windows-хоста, а
не сетевой инфраструктурой. Прямых точек пересечения с GridForge нет.

**Для GridForge:** не рекомендуется к заимствованию. Единственная
переносимая идея — детальная модель правил «по родительскому процессу/
сервису» теоретически интересна, если GridForge когда-нибудь вырастет в
сторону endpoint-агентов, но это не текущее направление продукта.

## Рекомендации

Отсортировано по объёму работы. «Быстро» — вписывается в уже существующие
паттерны GridForge (расписания сканов уязвимостей/кабелей). «Средне» —
новая, но контролируемая подсистема. «Крупно» — стратегическое решение, не
делать без явного запроса.

### 4.1 · Фоновый скан «кто новый в сети» — быстро

Существующий CIDR-скан (Разведка → Скан) сейчас запускается только вручную
и не запоминает базовый список. Добавить сравнение результата с уже
известными Node по группе/CIDR и заводить Incident/Signal на новый MAC/IP —
тот же паттерн, что уже отработан для расписаний сканов уязвимостей и
кабельного автоопроса, просто с новым источником данных.

Источник идеи: NetAlertX — непрерывное ARP/DHCP-обнаружение с алертом на
новое устройство.

### 4.2 · Apprise вместо ручной интеграции каждого канала уведомлений — быстро

Signal/Channel сейчас поддерживает ограниченный набор интеграций, каждая —
отдельный написанный вручную клиент. Библиотека Apprise (Python) даёт 80+
сервисов уведомлений одним общим интерфейсом — Telegram, Slack, email,
Matrix, ntfy и т.д. без написания клиента под каждый.

Источник идеи: NetAlertX — заявленные 80+ каналов через Apprise.

### 4.3 · Endpoint `/metrics` для Prometheus — быстро

Отдать число узлов/активных Incident/длительность последнего скана и т.п. в
формате Prometheus exposition — типовой FastAPI-эндпоинт без изменений в
схеме БД. Открывает интеграцию с уже существующим у пользователя стеком
мониторинга (Grafana).

Источник идеи: NetAlertX и ntopng — оба отдают метрики Prometheus «из
коробки».

### 4.4 · GeoIP/ASN рядом с внешними адресами — быстро

В Syslog, Capture и будущих находках — подписывать внешний IP страной/ASN
через локальную MaxMind GeoLite2-базу (офлайн, без внешних запросов на
каждый IP). Дёшево, только справочник + lookup-функция.

Источник идеи: Sniffnet — GeoIP/ASN прямо в интерфейсе трафика.

### 4.5 · Приёмник NetFlow/sFlow + дашборд «топ говорящих» — средне

Не копировать ntopng целиком (DPI, eBPF, Kubernetes-мониторинг) — начать с
узкого приёмника NetFlow v9/IPFIX (большинство Cisco 9300 в этом парке уже
умеют его отдавать без дополнительных агентов) и простого дашборда по
группе: топ хостов по трафику за период, топ пар источник-получатель.
Естественное продолжение уже существующего Capture, но непрерывное, а не
разовое.

Источник идеи: ntopng (потоковая модель), отчасти Arkime (идея
индексированной истории, но без полного PCAP).

### 4.6 · Правила жизненного цикла устройств — средне

Небольшой движок правил поверх уже существующей модели Node/Group:
автогруппировка по вендору (из уже собираемого `show version`), автопометка
«офлайн N дней» с предложением архивировать. Не требует новой модели
данных — только правила поверх существующей.

Источник идеи: NetAlertX — модуль Workflows.

### 4.7 · LLDP как второй источник для журнала кабелей — средне

CDP-автоопрос кабельных соединений уже сделан (Cisco-only, намеренно).
Расширение на LLDP для не-Cisco-оборудования — логичное продолжение, но
требует осторожного разбора табличного вывода (решено не делать LLDP/Junos
«вслепую» из-за разброса форматов между версиями ПО) — тестировать на
реальном выводе перед включением, как и было с CDP.

Источник идеи: LibreNMS и NetAlertX оба используют LLDP/CDP как основной
механизм топологии.

### 4.8 · OIDC SSO в дополнение к LDAP — средне

Сегодня вход — локальные учётки + LDAP-синхронизация. OIDC (Keycloak/Azure
AD/Google Workspace и т.п.) — частый корпоративный стандарт, которого пока
нет. Отдельная от LDAP авторизационная схема, но использует уже
существующую модель ролей/сессий.

Источник идеи: LibreDB Studio — OIDC SSO включён без разделения на тарифы.

### 4.9 · «Спроси про сеть» — read-only ИИ-отчёт по уже собранным данным — средне

У GridForge уже накоплен богатый структурированный контекст: находки
уязвимостей, находки AD/сетевого аудита, диффы бэкапов, журнал кабелей.
Ассистент, отвечающий на вопрос («что изменилось на LAB-2 за неделю»,
«какие узлы не проходят аудит порт-секьюрити») со ссылками на конкретные
записи, и жёстко ограниченный только чтением на уровне запроса к БД (не
полагаясь на то, что промпт «попросит» не писать) — прямое развитие уже
освоенных в GridForge паттернов отчётности (Vuln Register, Network Audit
report).

Источник идеи: LibreDB Studio — AI-агент с цитированием источников и
read-only на уровне драйвера/транзакции.

### 4.10 · Sync Node — модель мульти-сайта — крупно

Только если реально нужно единое окно для нескольких независимых
площадок/арендаторов (MSP-сценарий) — сейчас каждый инстанс GridForge
живёт полностью отдельно, без обмена данными. Строить эту модель без
конкретного заказчика/сценария преждевременно — архитектурное решение на
годы вперёд, а не фича одного релиза.

Источник идеи: NetAlertX — Sync Node, центральный хаб + периферийные узлы.

## Сознательно не берём

Не потому что плохие проекты — потому что решают другую задачу или
требуют архитектуры, несовместимой с философией GridForge «один инстанс,
SQLite/MySQL, без внешних кластеров».

**Полный стек Arkime (OpenSearch-кластер + распределённые сенсоры).**
Правильное решение для организации, которой нужен forensics-архив трафика
в масштабе всей сети на месяцы вперёд. GridForge сегодня — один инстанс на
площадку без выделенной кластерной инфраструктуры; заводить Elasticsearch/
OpenSearch только ради этой функции — несоразмерная цена. Если появится
конкретная compliance-причина хранить полный трафик подолгу — пересмотреть
отдельно, не походя.

**Fort Firewall — endpoint-агент на Windows-хостах.** GridForge — инструмент
для управления сетевой инфраструктурой (свитчи, роутеры), не
endpoint-security продукт. Управление firewall на рабочих станциях —
отдельный класс задач и отдельный продукт, смешивать в одну кодовую базу
не стоит.

**OpenWISP: полная PKI + push/pull для CPE/WiFi.** Осмысленно только если в
парке появятся устройства без постоянного прямого SSH-доступа (WiFi AP за
NAT, CPE у клиентов). Для текущего парка управляемых Cisco-свитчей с
прямой SSH-доступностью — это решение проблемы, которой пока нет.
