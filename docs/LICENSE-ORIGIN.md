# GridForge — происхождение кода и лицензионная чистота

Составлено: 2026-09-25. Это внутренняя подготовительная справка для
владельца — **не юридическое заключение**. Перед продажей или передачей
прав необходима проверка профессиональным юристом по интеллектуальной
собственности (см. §7) — этот документ облегчает такую проверку, не
заменяет её.

## 1. Резюме

**Код GridForge написан с нуля.** Ни одной строки не скопировано и не
адаптировано из исходного кода Zabbix (GPLv2) или любого другого
проприетарного/защищённого авторским правом продукта, не принадлежащего
владельцу GridForge. Из открытых проектов заимствовались только **идеи**
(что должна уметь система мониторинга) — не код, не схема базы данных, не
формат протокола, не текстовые шаблоны конфигурации.

Единственное, что в буквальном смысле «взято от других» — это набор
стандартных open-source библиотек (зависимости из `requirements.txt`),
используемых как внешние пакеты через обычный `import`, а не
скопированных построчно в код проекта. Это стандартная, юридически
рутинная практика для любого современного ПО — не то же самое, что
заимствование кода конкурирующего продукта. Подробности и единственные
пункты, требующие внимания перед продажей, — в §5.

## 2. Методология «чистой комнаты» (clean-room)

При разработке:
- Функциональность описывалась словами («нужна проверка доступности порта
  по TCP», «нужен аудит AD в духе категорий PingCastle») — реализация
  писалась по этому описанию, не по чужому исходному коду.
- Исходный код Zabbix **не читался и не копировался** ни на одном этапе.
- Готовые конфигурационные шаблоны Zabbix (share.zabbix.com и т.п.) **не
  скачивались** — наборы проверок построены с нуля поверх собственных
  сущностей `Probe`/`Watch`, идентификаторы SNMP (OID) брались из
  документации производителей оборудования (MIB-файлы вендоров), не из
  шаблонов Zabbix.
- Правило зафиксировано письменно и соблюдалось на протяжении всей
  разработки (см. `HANDOFF.md`, §8 «Правила разработки»).

## 3. Собственная терминология — и автоматическая проверка

GridForge использует полностью свою терминологию, не кальку с Zabbix:

| Zabbix (чужое) | GridForge (своё) |
|---|---|
| Host | Node |
| Item | Probe |
| History | Sample |
| Trigger | Watch |
| Event / Problem | Incident |
| Action | Signal |

Это не просто переименование «для вида» — совпадение имён сущностей
было бы прямым сигналом производной работы, даже при независимой
реализации логики. Поэтому в репозитории есть автоматический
тест-сторож (`tests/test_naming_purity.py`), который на **каждом**
прогоне тестов проверяет имена классов, таблиц БД, полей моделей и путей
API на отсутствие терминологии Zabbix (`host`/`item`/`trigger`/
`history`) и терминологии другого продукта того же владельца, NetOpsHub
(`Device`/`Alert`) — GridForge и его переносит по тем же правилам, не
копирует между своими же продуктами напрямую.

Тест ловит нарушения на практике, не только в теории: 2026-09-25 он
поймал случайную утечку (`dc_host`, `live_hosts` — поля, использовавшие
слово «host» в обычном сетевом смысле, не как сущность), нарушения были
переименованы (`dc_address`, `live_addresses`) в тот же день.

## 4. Собственная схема данных

База данных GridForge (`app/models.py`) спроектирована с нуля вокруг
терминологии из §3 — ни одна таблица или колонка не скопирована из схемы
Zabbix 1:1. Архитектура опроса тоже принципиально другая: GridForge
использует один asyncio-цикл с мин-кучей (`app/scheduler.py`), Zabbix —
несколько форкнутых процессов-пуллеров с общей очередью; это
архитектурное решение, а не косметика.

## 6. Что НЕ делалось (соблюдение собственных правил разработки)

- Исходный код Zabbix не открывался и не читался при написании функций.
- Готовые шаблоны мониторинга Zabbix не скачивались и не адаптировались.
- Между GridForge и NetOpsHub (оба принадлежат одному владельцу) код не
  копируется напрямую — функциональность переносится тем же способом,
  «от описания», с собственной терминологией и архитектурой.

3. Добавить в пользовательскую документацию/страницу «О программе»
   атрибуцию для `impacket` (по духу лицензии, см. §5) — сейчас такой
   страницы в интерфейсе нет.
4. Явно задокументировать в проекте (например, в `NOTICE`-файле или
   лицензионном соглашении конечного пользователя), что `asyncssh`
   используется под **EPL-2.0** (не GPL) и `ldap3` — под LGPLv3 как
   неизменённая динамически подключаемая библиотека.
5. Пройти чеклист «GridForge Rewrite Ledger» (интерактивный документ,
   отдельно у владельца) — построчная сверка каждого модуля со статусом
   «переписано с нуля».

## 8. Дисциплина независимой разработки как дополнительное свидетельство

Каждая функция GridForge проверялась вживую на реальной или honestly
воспроизведённой инфраструктуре (см. `HANDOFF.md`, §5) — реальные
SSH/SNMP-агенты, поднятый тестовый Active Directory, реальные пакеты
NetFlow/Syslog, реальный Keycloak для проверки OIDC, реальный внешний
API (MaxMind, Gemini). Это не юридическое доказательство само по себе,
но фиксирует независимую, поведенчески проверенную реализацию, а не
слепое копирование чужого кода «на глаз» — то, как ведётся разработка,
соответствует тому, что заявлено в §2.
