## Проблема / зачем

(счётчики, стена узлов, список инцидентов), но не даёт посмотреть на
метрики во времени рядом друг с другом. Единственный график, который
есть в проекте — мини-график одного `Probe` внутри карточки узла в

Владелец параллельно поднимал Prometheus+Grafana на отдельном хосте

(`Probe`+`Sample`+`Watch`, составной индекс `probe_id+taken_at`),
не хватает только UI-слоя для просмотра нескольких графиков вместе.

## Что делаем (scope)

1. Отдельная страница `graphs.html` — общий временной диапазон на
   весь открытый дашборд (выбор: 1ч/6ч/24ч/7д).
2. **Сохранённые, свободно собираемые дашборды, НЕ один зашитый
   набор** (решение 2026-09-30, пересматривает более раннее "без
   сущности, только URL" — см. "Модель данных"): владелец сам создаёт
   сколько угодно дашбордов под разные задачи (например "Коммутаторы
   MT"), даёт каждому имя и описание, переключается между ними.
3. **Внутри дашборда — несколько страниц** (решение 2026-09-30, по
   образцу Zabbix Dashboard Pages): один дашборд — это не плоский
   список панелей, а именованные вкладки внутри него, каждая — свой
   набор панелей. Пример реального сценария: дашборд "Коммутаторы MT",
   страница 1 — графики трафика/задержки, страница 2 — syslog этих
   узлов. Работа с временным диапазоном — общая на весь дашборд, не
   отдельно на каждую страницу (проще для первой итерации).
4. **Панель = один или несколько `Probe` на одном графике** — не
   только "график одного Probe": например "Download" и "Upload"
   одного интерфейса рядом на одной панели, разными цветами (по
   образцу связки `snmp_counter_rate` на приём/передачу).
5. **Виджет "stat"** — большое число (последнее значение проверки) +
   спарклайн (маленький график без осей/подписей) рядом, по образцу
   плиток "текущая скорость" — не только полноразмерный график.
6. **Виджеты "incidents" и "syslog"** (решение 2026-09-30, по итогам
   разбора, что уже показывают Zabbix/Grafana помимо графиков метрик):
   панель, показывающая не `Sample`, а инциденты или syslog-сообщения
   конкретного узла (или всех видимых узлов, если узел не выбран).
   `/api/syslog` уже поддерживает `node_id` как есть; `/api/incidents`
   — **проверено, не поддерживает** (только `include_resolved`, см.
   `app/main.py:1073`) — небольшое расширение эндпоинта нужно, не
   новый эндпоинт (см. API ниже). Без этого дашборд под коммутаторы
   показывал бы только цифры, без событий — как раз то, что уже есть
   на `index.html` (`incidents-body`, `event-feed`), но недоступно
   внутри свободно собираемого дашборда.
7. **Архитектура — расширяемая под будущие типы панелей.** Тип
   виджета — просто строка в JSON (`panels`/`pages`, см. "Модель
   данных"), не жёсткая схема на каждый тип — добавить новый тип
   панели в будущем (например источник данных, которого сейчас нет в
   проекте) не потребует миграции БД, только новый case в рендере на
   фронте. Ничего сверх line/area/stat/incidents/syslog сейчас НЕ
   реализуем (см. out of scope) — просто не закладываем архитектуру,
   которую придётся переделывать при первом же новом типе.
8. Backend: эндпоинт, отдающий `Sample` за диапазон времени с
   даунсэмплингом при большом объёме точек (чтобы не тянуть в браузер
   десятки тысяч точек за 7 дней) — вынести логику отдельно от уже
   существующего `/api/probes/{id}/samples` (тот — под мини-график в
   инвентаре и под спарклайн в stat-виджете, `limit`-based, не
   time-range-based — переиспользуется как есть, без изменений).
9. На дашборде (`index.html`) — вынести уже посчитанный, но не
   используемый `problem_nodes` из `build_dashboard` в панель "Топ
   проблемных узлов" (P0 из исследования агентом 2026-09-30, готовые
   данные простаивают).
10. Стрелка тренда (↑/↓/→) у critical/warning счётчиков — сравнение
    последних 2-3 часов с предыдущими на основе уже существующего
    `/api/dashboard/incident-trend`.

## Модель данных — новое/изменения

**Пересмотрено 2026-09-30**: более раннее решение "без сущности,
только URL-параметры" снято — владелец явно попросил именованные,
описываемые, переключаемые дашборды (как в Grafana), URL-параметрами
такое не покрыть (не сохранить имя/описание, не переключиться между
несколькими наборами).

Новая таблица, по образцу `Probe.params` (гибкая конфигурация —
JSON, а не жёсткая нормализация под каждое поле, тот же принцип, что
уже в проекте). **Три уровня, не два** (пересмотрено 2026-09-30 — добавлены
страницы внутри дашборда): `GraphDashboard` → список `pages` → у каждой
страницы список `panels`.

```python
class GraphDashboard(Base):
    __tablename__ = "graph_dashboards"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(128), nullable=False)
    description: Mapped[str | None] = mapped_column(Text, nullable=True)
    # [{"name": str, "panels": [Panel, ...]}, ...] — порядок списка
    # = порядок вкладок-страниц.
    pages: Mapped[list] = mapped_column(JSON, default=list)
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=_now)
```

**Форма `Panel` внутри `pages[i]["panels"]` зависит от `widget`** (тот
же принцип, что у `Probe.params`, зависящих от `Probe.kind`):

```jsonc
// widget: "line" | "area" | "stat" — метрики
{"widget": "line", "probe_ids": [12, 13], "label": "Трафик Gi1/1/2"}

// widget: "incidents" | "syslog" — события/логи, не Probe
{"widget": "incidents", "node_id": 7, "label": "Инциденты FLOOR-1"}
{"widget": "syslog", "node_id": null, "label": "Весь syslog"}
// node_id: null — без фильтра по узлу (все видимые ключу узлы,
// как сейчас работает /api/incidents и /api/syslog без параметра)
```

**Своей RBAC-проверки на уровне дашборда нет — переиспользуем то, что
уже есть.** Дашборд — это просто список ссылок на `Probe`/`Node`; когда
фронт запрашивает данные конкретной панели, каждый `probe_id` проходит
через уже существующий `require_probe_access` (`/samples/range`), а
каждый `node_id` — через `require_node_access`/уже встроенную
group-фильтрацию `/api/incidents` и `/api/syslog`. Если дашборд
ссылается на `Probe`/`Node` вне области ключа — конкретная панель
отдаст 404 или пустой список (как эти эндпоинты уже себя ведут), без
необходимости дублировать проверку области ещё и на самом
`GraphDashboard`.

## API — новые эндпоинты

### Данные графика

- `GET /api/probes/{id}/samples/range?since=...&until=...&max_points=...`
  — time-range выборка с даунсэмплингом, отдельно от текущего
  `limit`-based `/api/probes/{id}/samples` (тот не трогаем — им
  по-прежнему пользуются мини-график в инвентаре и спарклайн
  stat-виджета).

  **Даунсэмплинг — в Python, не в SQL.** Агрегация по временным
  корзинам через `GROUP BY` потребовала бы усечения даты, а синтаксис
  разный на SQLite (`strftime`) и MySQL (`DATE_FORMAT`) — та же
  ловушка диалектов, что уже стоила трёх багов при переходе на MySQL
  в 000. Вместо этого: один запрос тянет сырые `Sample` за
  `[since, until]` (для реалистичных интервалов опроса — разумный
  объём для одного запроса, не десятки миллионов строк), эндпоинт сам
  делит их на `max_points` равных по числу точек корзин в коде —
  единая логика для обоих движков, ничего диалект-специфичного.

  **В каждой корзине — и `value` (max), и `min`.** Среднее сглаживает
  реальные всплески значения, а именно всплески обычно и важны при
  разборе инцидента (кратковременный скачок трафика/задержки) — если
  усреднить, такой всплеск может стать незаметен после даунсэмплинга.
  `value` = max корзины — то, что рисуется как основная линия/заливка
  (см. UI ниже, тот же приём, что у консолидации MAX в классических
  графиках Zabbix/RRDtool); `min` возвращается отдельно, для
  тултипа/диапазона, в основной заливке не участвует. `ok` корзины —
  `false`, если хоть одна точка внутри `false` (тот же принцип "не
  прятать проблему", что уже в `silent`-логике `build_dashboard`).

### Сохранённые дашборды

Новый роутер `api_operate` (не `api_write`/admin-only) — управление
дашбордом не относится к инвентарю/правилам/каналам/ключам, которые
`ApiKeyRole` резервирует за admin; это ближе к запуску операций,
которые уже разрешены `operator` (см. `ApiKeyRole.operator` в
`models.py`).

- `GET /api/graph-dashboards` — список (`id`, `name`, `description`,
  без `pages`) — для переключателя дашбордов на странице.
- `POST /api/graph-dashboards` — создать `{name, description, pages}`.
- `GET /api/graph-dashboards/{id}` — полные данные, включая `pages`.
- `PUT /api/graph-dashboards/{id}` — обновить (переименование,
  описание, состав страниц/панелей).
- `DELETE /api/graph-dashboards/{id}` — удалить.

Новых эндпоинтов под `incidents`/`syslog`-панели не заводим, но
`/api/incidents` нужно **небольшое расширение**:

- `GET /api/incidents?node_id=...&include_resolved=...` — добавить
  необязательный `node_id`, фильтрующий уже полученную (после
  group-scoping) выборку по `Node.id` (тот же join `Incident → Watch →
  Probe → Node`, что там уже есть для проверки группы — фильтр по
  конкретному узлу ложится на него естественно, без нового join).
  Без параметра — поведение не меняется (все видимые ключу).
- `GET /api/syslog?node_id=...&limit=...` — уже поддерживает `node_id`,
  используется как есть.

### Переключатель дашбордов и страниц внутри них

Два уровня вкладок, не путать между собой:

- **Дашборды** — список сохранённых (`GET /api/graph-dashboards`),
  выпадающий список сверху страницы, плюс кнопка "Новый дашборд".
- **Страницы внутри открытого дашборда** — отдельный ряд вкладок под
  выбором дашборда (например "Коммутаторы MT" → вкладки "Метрики" /
  "Syslog"), плюс кнопка "Новая страница" на текущем дашборде.
- Форма дашборда: имя, описание (не обязательное). Форма страницы:
  имя, список панелей — добавить панель (выбрать widget: line/area/
  stat — тогда один или несколько `Probe`; incidents/syslog — тогда
  один узел или "все"), убрать панель, порядок.
- Общий диапазон времени (1ч/6ч/24ч/7д) — один переключатель на весь
  дашборд (все страницы сразу, см. out of scope про per-страничный
  диапазон), к панелям `incidents`/`syslog` не применяется (у тех
  своя пагинация через `limit`, не диапазон времени).

### Типы виджетов на панели

- **line** — как сейчас в `renderProbeChart`, просто полилиния по
  `value` (max корзины при даунсэмплинге).
- **area** — та же полилиния, плюс заливка от базовой линии (0) до
  `value` (не полноценная min/max-огибающая двумя линиями — так же,
  как консолидация MAX в классических графиках Zabbix/RRDtool: одна
  линия/заливка по максимуму корзины, `min` доступен только в тултипе
  точки). Это и есть тот внешний вид area-графика с примеров.
- **stat** — большое число (последний `Sample.value` через уже
  существующий `limit=1` на `/api/probes/{id}/samples`) + спарклайн
  рядом (тот же `limit`-based эндпоинт, `limit=30`, без осей/подписей,
  просто маленькая полилиния).
- **Многосерийная панель** — если у панели несколько `probe_ids`,
  каждый — отдельный вызов `/samples/range`, отрисовывается своей
  полилинией/заливкой своим цветом на одном SVG с общей осью Y (по
  образцу "Bits sent"/"Bits received" на одном графике). Цвета — из
  уже существующей палитры `style.css`, не новые.
- **incidents** — не график: рендер переиспользует логику
  `renderIncidentsGrouped` из `index.js` (уже используется для панели
  "Открытые инциденты" на дашборде) — выносим в `common.js`, чтобы не
  дублировать код между `index.html` и `graphs.html`. Данные —
  `GET /api/incidents?node_id=...` (без параметра — все видимые узлы).
- **syslog** — не график: компактный список сообщений, тот же принцип
  рендера, что в `syslog.js` (`refreshSyslog`), но без панели фильтров
  этой отдельной страницы — только сама лента. Данные —
  `GET /api/syslog?node_id=...&limit=30`. Полнотекстовый поиск (002)
  в панель на дашборде НЕ выносим на первой итерации — там он полезен
  как отдельный инструмент разбора, на дашборде важнее компактность.

## План проверки

- Живая проверка на реальных `Probe`/`Sample` из dev/prod-инстанса
  (не только синтетические тестовые данные) — сравнить, что график на
  новой странице показывает то же самое, что мини-график в инвентаре
  для того же probe за то же окно.
- Проверить поведение при большом диапазоне (7д) на probe с частым
  интервалом опроса — не должен тормозить/перегружать браузер.
- Проверить, что реальный известный всплеск/провал значения в данных
  виден на графике и после даунсэмплинга (не сглажен) — самый важный
  тест именно для решения "min/max, не среднее" выше.
- Панель "Топ проблемных узлов" на `index.html` — показывает те же
  узлы и в том же порядке, что уже отдаёт `problem_nodes` в
  `/api/dashboard` (готовые данные, только не были на UI).
- Стрелка тренда — сверить на реальных данных с известным ростом/
  падением числа инцидентов за последние 2-3 часа, не только на
  синтетике.
- Создать реальный дашборд "Коммутаторы MT" на живом инстансе с
  панелью на реальный `snmp_counter_rate` интерфейса (тот самый сценарий
  со скриншотов Zabbix/Grafana) — убедиться, что area-заливка визуально
  похожа на ожидаемый вид (не путать с line-виджетом).
- Многосерийная панель — реальные Download+Upload одного интерфейса на
  одной панели, разными цветами, не перепутаны местами.
- stat-виджет — большое число совпадает с последним `Sample` того же
  `Probe`, что уже видно в инвентаре.
- CRUD дашбордов — создать, переименовать, добавить/убрать панель,
  удалить; ключ с ролью `viewer` не может создать/изменить/удалить
  (403), `operator`/`admin` — может.
- Дашборд, ссылающийся на `Probe` вне области ключа с `group_id` —
  конкретная панель отдаёт 404 (не 500, не пустой график без объяснения).
- Создать дашборд с несколькими страницами (минимум 2) — переключение
  между страницами не теряет выбранный дашборд/диапазон времени.
- Панель `incidents`/`syslog` с конкретным `node_id` — показывает
  только события этого узла, не всех; с `node_id: null` — все видимые
  ключу (сверить с тем, что уже видно на `index.html`/`syslog.html`
  для того же ключа).
