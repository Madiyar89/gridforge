# 002 — Полнотекстовый поиск по syslog

Статус: draft

## Проблема / зачем

`GET /api/syslog` (`app/main.py:3457`) сейчас отдаёт только последние
`limit` сообщений (по умолчанию 100, максимум 500), с фильтром по
`node_id`/`source_ip` — поиска по тексту самого сообщения нет вообще.
UI (`static/syslog.html`/`syslog.js`) просто рендерит эту ленту; панель
«Поиск IP → hostname/пользователь» на той же странице — про другое
(IP/MAC-lookup), не про текст лога.

На практике при разборе инцидента нужно найти конкретную строку
("OSPF neighbor down", код конкретной SSH-ошибки и т.п.) среди
потенциально тысяч сообщений — сейчас это невозможно иначе, чем
листать последние 500 и `Ctrl+F` в браузере.

000 (`docs/specs/000-platform-foundations.md`) прямо называет эту
задачу причиной, по которой переход на MySQL нельзя было откладывать:
FTS5 (SQLite) и FULLTEXT INDEX (MySQL) — разный SQL-синтаксис на
каждом движке, и теперь, когда `gridforge-local` реально работает на
MySQL (не только теоретически dialect-агностичен), оба пути можно и
нужно проверить живым индексом, а не только на бумаге.

**Отдельное осознанное решение владельца (2026-09-30):** GridForge не
подключается к уже поднятому для NetOpsHub Graylog (`192.168.7.243`,
`graylog_client.py`) — свои логи ищем своим FTS, без внешней
зависимости. Тот же принцип, что уже применён к Prometheus+Grafana в
000: для объёма и назначения GridForge поднимать/подключать отдельный
поисковый стек — избыточно, встроенного индекса СУБД достаточно.
Корреляция с тем, что уже видит Graylog через NetOpsHub — отдельная,
не входящая в это ТЗ задача (см. out of scope).

**Требование к самому поиску — понятность, не только наличие.**
Большие системы (Graylog/ELK, Grafana Loki) требуют от пользователя
знать синтаксис запроса (`message:"x" AND NOT level:6`,
`{job="y"} |= "z"`) — для сетевого инженера, который открывает
страницу пару раз в неделю, это реальный барьер, не мелочь. GridForge
целится в противоположное: одно поле, обычные слова, без синтаксиса
для изучения — см. явные требования к UI ниже.

## Что делаем (scope)

1. Полнотекстовый индекс по `SyslogMessage.message`:
   - **SQLite**: virtual table `syslog_messages_fts` (FTS5, токенайзер
     `unicode61` — дефолтный, БЕЗ porter-стемминга: литеральное
     совпадение по словам предсказуемее для точных терминов из логов
     устройств, чем "down"/"downed"/"downing" через одну основу;
     `content=syslog_messages`, `content_rowid=id` — external content,
     не дублирует сами данные), синхронизация триггерами
     `AFTER INSERT/UPDATE/DELETE` на `syslog_messages`.
   - **MySQL/MariaDB**: `ALTER TABLE syslog_messages ADD FULLTEXT INDEX
     ix_syslog_messages_message (message)` — обычный индекс поверх
     существующей колонки, новая таблица не нужна.
2. Новый query-параметр `q` у существующего `GET /api/syslog`:
   при непустом `q` — полнотекстовый поиск, сочетается с уже
   существующими `node_id`/`source_ip`/`limit`. Пустой/отсутствующий
   `q` — прежнее поведение без изменений. Построение запроса —
   диалект-специфичное, но оба пути параметризованы (не строковая
   конкатенация):
   - **MySQL**: `MATCH(message) AGAINST(? IN NATURAL LANGUAGE MODE)` —
     в natural language mode нет операторов, экранировать по сути
     нечего, сам режим безопасен по конструкции.
   - **SQLite FTS5**: каждое слово `q` оборачивается в двойные кавычки
     перед подстановкой (`"слово1" "слово2"`) — форсирует буквальное
     совпадение и блокирует спецсимволы FTS5 (`*`, `^`, `:`, скобки)
     как операторы запроса.
3. Миграция индекса — своя функция в `app/db.py` (механизм создания FTS5
   и FULLTEXT принципиально разный, не подходит под уже существующий
   `_migrate_missing_columns()`, который только про обычные колонки),
   идемпотентная: проверка перед созданием через `sqlite_master`
   (SQLite) / `information_schema.STATISTICS` (MySQL), вызывается из
   той же точки старта, что и `_migrate_missing_columns()`.
4. UI: поле поиска на `syslog.html` рядом с `#syslog-node-filter` (тот
   же `.form-row`), `refreshSyslog()` в `syslog.js` добавляет `q` в
   query string при непустом значении.

## Что НЕ делаем (out of scope)

- Time-range фильтр (`since`/`until`) на `/api/syslog` — сейчас его
  тоже нет (только `limit` последних N), но это отдельная, соседняя
  задача — не мешаем в одну сессию.
- Полнотекстовый поиск по другим текстовым полям (`Backup.content`,
  `ScenarioResult.output`, находки `VulnScan` и т.д.) — только
  `SyslogMessage.message` в этом ТЗ, остальные — отдельные ТЗ при
  необходимости.
- Продвинутый синтаксис запроса **для пользователя** (булевы операторы,
  фразовый поиск в кавычках и т.п.) — GridForge не документирует и не
  поддерживает такой ввод сверх обычных слов. Не путать с
  экранированием спецсимволов на backend перед подстановкой в
  FTS5/MATCH-запрос — это обязательная часть реализации (см. scope,
  п.2, и план проверки), а не то, от чего мы отказываемся.
- Ретеншн/архивация старых syslog-сообщений — вопрос хранения, не
  поиска.
- Живая проверка и раскатка на проде (192.168.7.244) — по решению из
  000 прод остаётся на SQLite и не трогается; работаем и проверяем на
  `gridforge-local` (MySQL) в первую очередь, SQLite/FTS5-путь —
  параллельно на dev.

## Модель данных — новое/изменения

- SQLite: новая virtual table `syslog_messages_fts` (FTS5, external
  content на `syslog_messages`) + 3 триггера синхронизации
  (`INSERT`/`UPDATE`/`DELETE`). Основная таблица `syslog_messages` не
  меняется.
- MySQL/MariaDB: `FULLTEXT INDEX` поверх существующей колонки
  `message` — новых таблиц/колонок нет.
- Миграция — новая функция (условное имя `_ensure_syslog_search_index()`)
  в `app/db.py`, диалект-ветвление по уже существующему `_IS_SQLITE`,
  вызывается при старте вместе с `_migrate_missing_columns()`.

## API — новые эндпоинты

Не новый эндпоинт — новый параметр существующего:

- `GET /api/syslog?q=<текст>` (+ уже существующие `node_id`,
  `source_ip`, `limit`) — при непустом `q` результат отфильтрован
  полнотекстовым поиском по `message`, порядок — как сейчас, по
  `received_at DESC`.

## UI — что на странице

- `static/syslog.html`/`syslog.js`: поле поиска в `.form-row` рядом с
  `#syslog-node-filter`, `refreshSyslog()` добавляет `q` в путь запроса
  при непустом значении.
- **Подсветка совпадения в тексте сообщения — обязательный пункт, не
  nice-to-have.** Понятность результата — явная цель этого ТЗ (см.
  выше), а не только факт наличия поиска: пользователь должен сразу
  видеть, почему конкретное сообщение нашлось, не перечитывать всю
  строку в поисках совпадения. Оборачиваем найденные слова в
  `<mark>` (или свой класс с токеном `--warn`/`--info` из
  `style.css`, не изобретаем новый цвет).
  **Реализация — на фронте, не в БД**: SQLite даёт встроенный
  `highlight()`, у MySQL FULLTEXT такого нет — если положиться на
  нативную функцию, подсветка будет вести себя по-разному на двух
  движках (000 требует проверять оба одинаково). Backend отдаёт
  `message` как есть; `syslog.js` уже делает `escapeHtml()` — поверх
  уже экранированного текста оборачиваются в `<mark>` вхождения слов
  из `q` (регистронезависимо, по границам слов). Один код для обоих
  движков, и оборачивание идёт поверх уже безопасного текста, а не до
  экранирования.
- **Никакого синтаксиса запроса для пользователя.** Плейсхолдер поля —
  простой пример на обычных словах (`например: OSPF neighbor down`),
  не документация по FTS5/MySQL MATCH. Если движок вернёт синтаксическую
  ошибку на спецсимволах ввода (кавычка, `*`, и т.п.) — экранировать
  ввод перед запросом на backend, не показывать пользователю ошибку
  СУБД. Это прямое следствие решения из "Проблема/зачем" — не
  перекладываем сложность поискового синтаксиса на пользователя.

## План проверки

- Живая проверка на обоих движках (SQLite dev + MySQL `gridforge-local`)
  — реальные syslog-сообщения через уже работающий `syslog_server.py`
  (UDP-пакет) или прямая вставка для теста; поиск по подстроке слова
  находит сообщение на обоих движках.
- Пустой результат поиска — пустой список, не ошибка 500.
- Существующие фильтры (`node_id`, `source_ip`, `limit`) продолжают
  работать как с `q`, так и без него.
- Спецсимволы в `q` (кавычка, `*`, `AND`/`OR` как обычное слово в
  тексте лога) — не должны отдавать ошибку СУБД пользователю; ввод
  экранируется на backend до подстановки в FTS5/MATCH-запрос.
- Подсветка совпадения — проверить на реальном найденном сообщении, что
  подсвечивается именно искомое слово, а не всё сообщение целиком.
- Полный набор тестов прогнать против MySQL-инстанса (как в 000, не
  только против SQLite по умолчанию в `conftest.py`).
