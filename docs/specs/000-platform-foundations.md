# 000 — Платформенные основы: дизайн, разработка, SQLite→MySQL

Статус: draft

## Проблема / зачем

001 (графики), 002 (поиск логов), 003 (SNMP-метрики) — три отдельных
фичи, но у них общие сквозные вопросы, которые нельзя решать заново в
каждом ТЗ по отдельности: каким должен выглядеть новый UI, по каким
правилам пишется новый код, и на чём это всё должно надёжно работать
(SQLite сейчас везде, MySQL — опционально в коде, но НИГДЕ не
задеплоено и не проверено вживую). Этот файл — не новая фича, а
зафиксированные решения/ограничения, на которые 001/002/003 ссылаются,
вместо того чтобы каждый раз пересогласовывать заново.

## Дизайн и стиль — ничего нового не придумываем

У проекта уже есть готовая дизайн-система в `static/style.css`
(693 строки, CSS custom properties в `:root`): тёмная тема,
токены `--bg/--surface/--surface-2/--border/--text/--text-dim`,
цвета серьёзности `--crit/--warn/--info/--ok` (каждый с парой
основной+фон), моноширинный шрифт для данных (`--mono`), сайдбар
с двумя состояниями ширины. Все новые страницы (`graphs.html`,
переработанный `syslog.html`) обязаны использовать существующие
токены, а не заводить свою палитру/шрифты — так же, как уже сделано
во всех текущих страницах.

**Правило**: перед версткой новой страницы — посмотреть, есть ли уже
подходящий класс/компонент в `style.css` (панели `.panel`, `.stat`,
`.incident-row` и т.п. с дашборда) и переиспользовать, а не писать
дубликат с тем же смыслом под новым именем класса.

## Разработка — конвенции, уже действующие в проекте

Не вводим новых — фиксируем те, что уже есть, чтобы 001/002/003 их не
нарушили:

- Vanilla HTML/CSS/JS без шага сборки: `static/<page>.html` +
  одноимённый `<page>.js`, общий `common.js` — шапка/навигация/
  API-хелперы (`api()`, `timeAgo()`, `escapeHtml()` и т.п.). Новые
  страницы `graphs.html` — по этому же паттерну.
- Своя терминология, не калька с Zabbix/NetOpsHub — проверяется
  механически `tests/test_naming_purity.py`. Для 003 (SNMP-шаблоны) —
  можно брать OID из открытой документации/MIB вендора, НЕЛЬЗЯ брать
  формулировки/имена из официальных Zabbix-шаблонов (см. комментарий
  в `app/models.py` про `Template`).
- Миграции схемы — вручную в `app/db.py:_migrate_missing_columns()`,
  не Alembic. Любая новая колонка (например, под индекс FTS для 002
  или новую сущность для 003, если выберем вариант B) обязана туда
  попасть, иначе "локально работает, на проде колонки нет".
- Секреты (SNMP community/пароли) — через `secrets_crypto`, тот же
  ключ `data/secret.key`, никогда в открытом виде в `Probe.params`.
- Живая проверка обязательна для фич, трогающих реальные протоколы
  (SNMP, syslog) — не только юнит-тесты на синтетике, см. тон
  разработки в `CLAUDE.md`.

## SQLite → MySQL — реальное состояние и что нужно решить

**Текущее состояние (проверено 2026-09-30)**: MySQL/MariaDB
поддерживается кодом через `GRIDFORGE_DATABASE_URL` (добавлено
2026-09-20, "как в Zabbix" — осознанный выбор на масштаб продакшена),
код в `app/db.py` уже дialect-агностичен (без SQLite-специфичного
`PRAGMA`/`IF NOT EXISTS`, где это важно). **НО**: ни `docker-compose.yml`
локального, ни продового инстанса не задают `GRIDFORGE_DATABASE_URL`
— оба реально работают на SQLite. MySQL-путь существует только в коде,
никогда не был поднят и проверен вживую. Известный документированный
пробел: read-only ИИ-отчёт (`/api/ask`) на MySQL **честно отказывает**
— там нужна отдельная read-only учётка на уровне СУБД, которую
GridForge сам не заводит (см. `README.md`).

**Почему это важно именно сейчас**: 002 (поиск логов) планирует
FTS5 (SQLite) / FULLTEXT INDEX (MySQL) — это **разный SQL-синтаксис**
на каждом движке, значит первая фича, которая реально требует, чтобы
оба пути были не просто теоретически совместимы, а физически
работали и были проверены живым MySQL-инстансом, а не только SQLite,
на котором всё разрабатывается по умолчанию.

**Решение владельца (2026-09-30) — закрыто, не открытый вопрос:**

1. **MySQL/MariaDB поднимаем сейчас, не откладываем.** Разработка на
   SQLite с "доделаем MySQL потом" осознанно отклонена — по опыту
   владельца это создаёт вопросы с миграцией задним числом. Значит
   001/002/003 с этого момента разрабатываются и проверяются сразу на
   MySQL/MariaDB, не на SQLite.
2. **Проверять нужно сейчас**, не откладывать на отдельный заход —
   живая проверка MySQL-пути (не только код, который теоретически
   dialect-агностичен) обязательна до того, как 002 (FTS/FULLTEXT)
   считается готовой.
3. **Перенос существующих данных из SQLite в MySQL — тоже делаем**,
   не выносим в неопределённое будущее. Существующая БД (текущие
   Node/Probe/Sample/Incident и т.д. в рабочем WSL-инстансе) должна
   переехать, а не остаться заброшенной параллельно с новой MySQL.
4. **Где именно сейчас работаем**: только WSL-kali (`gridforge-local`,
   `/mnt/e/NetOpsHub-scaffold/gridforge-local`, localhost:8100) — **не**
   на боевом сервере (192.168.7.244). Прод не трогаем, пока переход на
   MySQL не проверен полностью локально.

**Конкретный план перехода (уточняется на этапе исполнения, порядок
шагов):**
1. Добавить сервис `mysql`/`mariadb` в `docker-compose.yml`
   (и в репозитории `/tmp/gridforge-app`, и в развёрнутом
   `gridforge-local`) — отдельный контейнер, volume под данные СУБД,
   пароль/учётка через переменные окружения (не хардкодить).
2. Задать `GRIDFORGE_DATABASE_URL` у сервиса `gridforge`, указывающий
   на новый MySQL-контейнер.
3. Написать разовый скрипт переноса данных SQLite → MySQL (такого
   скрипта в проекте сейчас нет — проверено, `grep -rliE 'migrat'` по
   `app/`/`deploy/` ничего профильного не находит). Перенос таблица за
   таблицей через SQLAlchemy-модели (не сырой SQL-дамп — типы данных
   между SQLite и MySQL не идентичны, например `Boolean`/`JSON`).
4. Прогнать существующий набор тестов (см. `CLAUDE.md` про
   docker-based прогон pytest в этом окружении) против MySQL-инстанса,
   не только против SQLite по умолчанию в `conftest.py`.
5. Живая проверка: поднять `gridforge-local` на MySQL, пройтись по
   ключевым страницам (дашборд, инвентарь, аудит) — данные после
   переноса видны и совпадают с тем, что было на SQLite.
6. Только после этого — переходить к реализации 002 (FTS/FULLTEXT) на
   уже работающем MySQL-инстансе.
